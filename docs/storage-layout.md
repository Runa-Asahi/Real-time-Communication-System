# 数据存储位置总览（工程师版）

本文回答三个问题：**每个文件是什么**、**谁是权威副本**、**跨进程是怎么同步的**。
所有路径都相对"数据根目录"（命令行参数给出），程序不会写到别处。

---

## 1. 一张图看清所有目录

```
<项目根>\
├─ data-im-server\                     ← 服务端数据根（scripts\run-im-server.bat 默认）
│  ├─ state.json                       ★ 服务端账号库（权威）：users / accounts / 开通关系 / 好友 / 群 / 绑定
│  ├─ state.json.prev                  上一代快照（原子发布的回滚点；主文件损坏时用 --recover 回退）
│  ├─ .lock                            目录独占锁（同一目录只允许一个进程打开）
│  └─ im-server\
│     ├─ server-identity.json          服务器实例标识（客户端据此判断本地聊天库是否属于本服务器）
│     ├─ server-chat.db                ★ 服务端消息库（SQLite，--im-sqlite）：会话 / 消息 / 收件人 / 投递游标
│     ├─ server-chat.db-wal, -shm      SQLite WAL 附带文件（正常运行时存在）
│     └─ state.json                    旧 JSON 日志后端（未加 --im-sqlite 时才用；与 server-chat.db 二选一）
│
├─ data-im-a\  data-im-b\              ← 控制台客户端数据根（每个终端一个，避免互相抢锁）
│  └─ im-client\
│     └─ <host>_<port>\                ← 按"服务端身份"分目录（127.0.0.1_9500 这种）
│        └─ <账号目录名>\               ← 登录时用的标识（微X号；非 ASCII 会被转义）
│           ├─ domain\                 ← 该账号在**本机**的领域库
│           │  ├─ state.json           ★ 本机领域数据：资料 / 好友 / 群 / 开通关系 / 绑定
│           │  ├─ state.json.prev      上一代快照
│           │  └─ .lock                领域库目录锁
│           ├─ QQ\                     ← 聊天通道目录之一（服务名 = 目录名）
│           │  ├─ chat.db              ★ 本机聊天库（SQLite）：会话 / 消息 / 待发送 / 同步游标
│           │  ├─ client-identity.json 聊天库归属（服务器实例 + 账号 + 设备号）
│           │  └─ .lock                聊天库目录锁（一个服务一把锁）
│           ├─ Wechat\ …               微信通道：同上
│           └─ Weibo\ …                微博通道：同上（号码与 QQ 相同时也不会互相覆盖）
│
└─ data-im-gui\                        ← GUI 客户端数据根（--data-root，默认 data-im-gui）
   └─ im-client\<host>_<port>\<账号目录>\{domain, QQ, Wechat, Weibo}   结构同上
```

要点：

- **领域库与聊天库永远分两层目录**：两者各要独占自己那层的 `.lock`，同目录会互相拒绝启动。
- **聊天库按服务再分一层**：QQ 与微博按课程约定共用号码，只有分目录才能各存各的历史。
- 一个数据根可以同时跑多个客户端（各自一个"本人"视角的完整领域副本），互不干扰。

## 2. 谁是权威（同一份数据可能有多个副本时）

| 数据 | 权威副本 | 谁写 | 服务端读它吗 |
| --- | --- | --- | --- |
| 微X号 / 服务号 / 密码 | **服务端** `<数据根>\state.json`（认证用）；客户端本机 `domain\state.json` 也有一份 | 客户端注册/开通 → 通过 IM 的 `REGISTER` 登记到服务端；服务端自己也可 `--init-demo` 写 | 是：每次 LOGIN 前"读穿" |
| 开通关系（本人有哪些服务） | 同上（两处都有；以服务端那份为准判定能否登录） | 客户端开通 → 随 `REGISTER` 补登到服务端 | 是 |
| 好友关系 | 客户端本机 `domain\state.json`（用户操作的地方）；服务端 `state.json` 是**镜像** | 客户端加/删 → 随 `REGISTER` 镜像到服务端 | 是：判定"是不是好友"用的是服务端那份 |
| 用户资料（昵称/所在地/…） | 客户端本机 `domain\state.json` | 客户端界面 | 否（只在服务端登记时写入一次初值） |
| 群与群成员 | 客户端本机 + 服务端演示数据（`--init-demo` 写入 12 个群） | 客户端界面（群操作） | 是：群消息投递前的成员判定 |
| 聊天消息 | **服务端** `im-server\server-chat.db`；客户端 `chat.db` 是各自的历史副本 | 服务端落库并投递；客户端落地后回 ACK | —（服务端就是中心） |
| 投递游标 / 未读 | 服务端 `delivery_cursors` + 客户端 `sync_cursors` | 双方各自推进 | — |
| 登录态（谁在线） | **内存**（不落盘） | — | 是 |
| 服务器实例标识 | 服务端 `im-server\server-identity.json` | 首次启动生成 | 是 |

> **为什么会有两份账号库**：客户端要先能登录、才能用界面；而聊天认证必须问服务端。
> 于是本机存一份（没有服务端也能看资料/好友/群），服务端存一份（认证与授权）。
> 两份靠 `REGISTER`（见第 4 节）对齐，**不做双向同步**——服务端不会反向改客户端的数据。

## 3. 数据文件与命令行的对应关系

| 场景 | 命令 | 用到的目录 |
| --- | --- | --- |
| 控制台（含聊天） | `fanlx_app.exe --data-dir data-im-a --im-host 127.0.0.1 --im-port 9500 --im-sqlite` | `data-im-a\im-client\127.0.0.1_9500\<微X号>\…` |
| GUI | `fanlx_gui.exe --host 127.0.0.1 --port 9500 --data-root data-im-gui` | `data-im-gui\im-client\127.0.0.1_9500\<微X号>\…` |
| 服务端 | `scripts\run-im-server.bat`（或 `fanlx_app.exe --data-dir data-im-server --im-server --im-sqlite`） | `data-im-server\state.json` + `data-im-server\im-server\…` |
| 旧数据迁移 | `fanlx_app.exe --data-dir X --im-migrate [--im-migrate-dir Y]` | 把旧 JSON 服务端日志迁进 SQLite 消息库 |

服务端与客户端**必须用不同的数据根**：同一目录的 `.lock` 只允许一个进程。
`scripts\run-im-server.bat` 会在启动前检查 `<数据根>\state.json`：空目录 / `schemaVersion=1` /
缺 `password` 时把旧目录改名保留为 `<数据根>.legacy-<时间戳>` 再自动 `--init-demo`。

## 4. 跨进程同步：`REGISTER`（账号登记）

问题：客户端注册只写本机 `domain\state.json`，服务端认证查的是**它自己**的 `state.json`。
两份文件互不相通，于是"注册完密码也对，却登不上"——重启服务端也没用（账号压根不在服务端库里）。

解决：客户端在**登录前**、以及需要时（登录被拒、开通服务后切通道）通过 IM 发一条 `REGISTER`：

```
REGISTER  sender = 微X号
          text   = {"password": "...", "nickname": "...", "birthDate": "...", "location": "...",
                    "services": [{"service": "QQ", "accountId": "2026001"}, ...],
                    "friends":  [{"service": "QQ", "accountId": "2026002"}, ...]}
→ REGISTER_OK | ERROR（原因原样回给界面）
```

服务端侧（`ServerAccountRegistrarFanLX`）：

1. 账号不存在 → `registerWeiXUser`（只建微X号，**不捆绑**任何服务，与课设要求一致）；
   账号已存在且密码一致 → 幂等成功；密码不一致 → 拒绝（不区分"不存在/密码错"，避免枚举账号）。
2. `services`：为本人补建并开通列出的服务（已存在的不改写号码）——领域层要求"以微X身份登录"，
   因此登记时用同一份凭据临时建立微X会话，做完立即注销。
3. `friends`：把客户端**已经成立**的好友关系镜像进服务端目录（`mirrorFriendship`：不重复校验
   "对端确认登录"，那一步客户端加好友时已经做过）。
4. 全部写入走**候选事务 + 原子发布**：要么整份新快照落盘，要么完全不变（不会写坏账号库）。

"服务端无状态"体现在 `ImServerFanLX::OptionsFanLX::refreshAccounts`：每次认证前读穿持久化快照
（只有文件真的变了才重新解析，`PersistenceApplicationFanLX::reloadIfChangedFromDisk`）。
因此：

> **注册之后不需要重启服务端**；服务端重启后账号与开通关系同样还在（都在 `state.json` 里）。
> 已由 `gui_behavior` 的 t69 逐步验证：未登记 → 拒绝；只登记微X → 拒绝且提示"服务端还没有为微X号 X 开通 QQ 服务"；
> 带服务与好友登记 → **同一个服务端进程**立刻能登录并成功投递消息；停掉服务端重开 → 仍能登录。

## 5. 常见问题定位表

| 现象 | 原因 | 处置 |
| --- | --- | --- |
| 注册成功、密码也对，聊天登录报"用户名或密码错误" | 该账号只在客户端本机注册，服务端账号库里还没有它 | 客户端会在登录被拒时自动 `REGISTER` 后重试；若仍失败，看界面提示的服务端原因（服务端没启动 / 版本旧） |
| 报"服务端还没有为微X号 X 开通 QQ 服务" | 服务端认识这个微X号，但没为它开通该服务 | 在客户端「开通管理」开通后重新登录（登录时会补登该服务） |
| 报"单聊目标必须是好友" | 好友只加在本机，没镜像到服务端 | 重新登录（会带好友一起登记），或确认对端号码在服务端存在 |
| 报"账号已有在线会话" | 单设备策略：同一账号第二处登录被拒 | 先注销旧会话（另一台客户端退出） |
| 报"无法独占数据目录 Win32=32" | 同一数据目录被另一个进程打开 | 换数据根；旧进程退出后可直接重启（锁文件不必删） |
| 报"未知 schemaVersion" / "用户缺少登录密码" | 旧格式快照 | 用 `scripts\run-im-server.bat`（自动重建）或手工 `--init-demo` |
| 客户端报"聊天数据库归属不符" | 目录被误用：库内身份（账号 / 服务器地址 / 端口 / 格式）与本次登录不一致 | 检查该账号目录是否放对了位置。注意"服务端换了库（实例号过期）"不会报错：旧库会被自动改名归档为 `*.legacy-<时间戳>`，并按当前实例新建 |
| 添加好友报"对端平台账号不存在" | 对端账号只存在于**服务端**（别人在别的客户端注册/开通的），本机副本里没有它 | 客户端会先向服务端查询（`LOOKUP`，用本人当前服务凭据校验）并把对端导入本机副本，再自动继续；若服务端也没有该号码，说明对方未注册或未开通该服务 |
| 注册完能登录、但主界面聊天页显示"未连接：本人还没有开通任何下级服务" | 这是**正常状态**而不是错误：新注册的微X号按课设要求不捆绑任何下级服务，因此没有聊天通道 | 到「账号与服务 → 开通管理」填号码并「开通所选服务」；开通后聊天页自动连上（开通时会把该服务登记到服务端） |
| 登录窗口一直不放行 | 微X号不存在或密码错（身份认证失败） | 留在登录界面重试；忘记密码就用另一个账号，或到服务端数据目录重新 `--init-demo` |
